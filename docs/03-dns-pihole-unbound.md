# 03 – DNS: Pi-hole + Unbound

This is the core of the setup. Pi-hole provides blocking, caching, logging and the web
UI. Unbound provides DNSSEC validation and encrypted upstream DNS.

## Design

```text
LAN client
  │  DNS :53
  ▼
Pi-hole FTL v6
  │  blocklists + cache + local records
  │  upstream = 127.0.0.1#5335
  ▼
Unbound 1.17
  │  root trust anchor (DNSSEC validation)
  │  forward-zone "." over TLS
  ▼
Cloudflare 1.1.1.1 / 1.0.0.1 on port 853
```

Two details are important:

1. **Pi-hole's DNSSEC setting is `false`.** Unbound is the component that validates
   DNSSEC. Pi-hole simply forwards to it. This is a valid split of responsibilities.
2. **Unbound is not recursive in the final configuration.** It validates and then
   forwards to Cloudflare over DNS-over-TLS. The original recursive configuration is
   still present as `pi-hole.conf.bak` (the same file without the `forward-zone` block).
   This matches the "Pi-hole with Unbound, later through Cloudflare" history.

## Pi-hole installation

Pi-hole v6 was installed with the official installer. At scan time:

```text
Core version : v6.4.3
Web version  : v6.6
FTL version  : v6.7
```

Install or upgrade:

```bash
curl -sSL https://install.pi-hole.net | bash
# later
sudo pihole -up
```

The installer writes `/etc/pihole/pihole.toml`. In v6 this file replaces most of the old
`setupVars.conf` workflow.

### Key Pi-hole settings

| Setting | Value | Notes |
| --- | --- | --- |
| `dns.upstreams` | `["127.0.0.1#5335"]` | All queries go to Unbound |
| `dns.port` | `53` | Standard DNS |
| `dns.listeningMode` | `LOCAL` | Only directly attached subnets |
| `dns.dnssec` | `false` | Validation happens in Unbound |
| `dns.bogusPriv` | `true` | Reject private PTR lookups upstream |
| `dns.domain` | `lan` | Local domain |
| `dhcp.active` | `false` | Router is the DHCP server |
| `webserver.domain` | `pi.hole` | Web UI name |
| `webserver.port` | `80o,443os,[::]:80o,[::]:443os` | HTTP + self-signed HTTPS |
| `webserver.acl` | `""` | No IP restriction |
| `ntp` | enabled | Pi-hole also serves NTP |

The web UI uses a self-signed certificate:

```text
Subject: CN = pi.hole
Issuer:  CN = pi.hole, O = Pi-hole, C = DE
Valid:   2025-04-26 to 2055-04-26
```

Browsers will warn until the certificate is trusted or replaced.

## Unbound installation and configuration

```bash
sudo apt update
sudo apt install unbound
```

The Debian package ships `/etc/unbound/unbound.conf` containing only:

```conf
include-toplevel: "/etc/unbound/unbound.conf.d/*.conf"
```

The Pi-specific file is `/etc/unbound/unbound.conf.d/pi-hole.conf`.

### Final configuration (with Cloudflare DoT)

```conf
server:
    verbosity: 0
    interface: 127.0.0.1
    port: 5335
    do-ip4: yes
    do-udp: yes
    do-tcp: yes
    do-ip6: no
    prefer-ip6: no

    harden-glue: yes
    harden-dnssec-stripped: yes
    use-caps-for-id: no

    edns-buffer-size: 1232
    prefetch: yes
    num-threads: 1
    so-rcvbuf: 1m

    private-address: 192.168.0.0/16
    private-address: 169.254.0.0/16
    private-address: 172.16.0.0/12
    private-address: 10.0.0.0/8
    private-address: fd00::/8
    private-address: fe80::/10

server:
    tls-cert-bundle: /etc/ssl/certs/ca-certificates.crt
forward-zone:
    name: "."
    forward-tls-upstream: yes
    # Cloudflare DNS
    forward-addr: 2606:4700:4700::1111@853#cloudflare-dns.com
    forward-addr: 1.1.1.1@853#cloudflare-dns.com
    forward-addr: 2606:4700:4700::1001@853#cloudflare-dns.com
    forward-addr: 1.0.0.1@853#cloudflare-dns.com
```

The full file, including the explanatory comments from the original, is in
[`configs/unbound/pi-hole.conf`](../configs/unbound/pi-hole.conf). The original
recursive variant is in
[`configs/unbound/pi-hole-recursive.conf.example`](../configs/unbound/pi-hole-recursive.conf.example).

DNSSEC validation is enabled by the Debian default trust anchor:

```conf
# /etc/unbound/unbound.conf.d/root-auto-trust-anchor-file.conf
server:
    auto-trust-anchor-file: "/var/lib/unbound/root.key"
```

### Caveats in this configuration

- `do-ip6: no` disables IPv6 transport. The four IPv6 forwarders in the `forward-zone`
  are therefore not used; only `1.1.1.1` and `1.0.0.1` over IPv4 are effective. This is
  harmless but confusing. Either remove the IPv6 forwarders or set `do-ip6: yes`.
- `private-address` still lists the RFC1918 ranges, which is fine. If you change your
  LAN to a different range, update it.
- `interface: 127.0.0.1` means Unbound is not reachable from the LAN. Only Pi-hole on
  the same host can use it. This is intentional.
- Unbound listens on port 5335, not 53, so it does not conflict with Pi-hole.

### Switching back to full recursion

Remove the `forward-zone` block, keep `auto-trust-anchor-file`, and optionally set
`root-hints: "/var/lib/unbound/root.hints"`. Then restart Unbound:

```bash
sudo systemctl restart unbound
```

Full recursion removes the dependency on Cloudflare but sends queries directly from your
public IP to the root and authoritative servers. The current DoT setup hides queries
from the local network/ISP and is faster.

## Verification

```bash
# Pi-hole is up and listening
sudo pihole status

# Unbound is listening
sudo ss -ulpn | grep 5335

# Normal resolution through Pi-hole
dig +short cloudflare.com @127.0.0.1

# DNSSEC must fail for a deliberately broken domain
dig +noall +comments dnssec-failed.org @127.0.0.1 | grep status
# expected: status: SERVFAIL

# ...and succeed for a valid domain
dig +noall +comments cloudflare.com @127.0.0.1 | grep status
# expected: status: NOERROR

# Query Unbound directly
dig +short example.com @127.0.0.1 -p 5335

# Blocklist size
sudo pihole -g -q 2>/dev/null || true
```

Observed results at scan time:

```text
dnssec-failed.org via Pi-hole : SERVFAIL
cloudflare.com via Pi-hole    : NOERROR
dnssec-failed.org via Unbound : SERVFAIL
gravity domains               : 380333
```

## Troubleshooting DNS

| Symptom | Check |
| --- | --- |
| No DNS on LAN | Is the router handing out `192.168.1.10`? Is port 53 reachable? |
| Pi-hole up but no resolution | Is Unbound running? `systemctl status unbound` |
| `SERVFAIL` for everything | DNSSEC validation failure or upstream blocked; check `dig @127.0.0.1 -p 5335` and Unbound logs |
| Slow resolution | Check `use-stale-cache`, upstream latency, and whether Unbound is forwarding to IPv6 addresses it cannot use |
| Pi-hole web UI inaccessible | Ports 80/443 are served by FTL, not Apache/nginx; check `ss -tlnp` |
| Blocking not working | `pihole -g`, check gravity count, check client is actually using Pi-hole |

Useful logs:

```bash
sudo journalctl -u pihole-FTL -f
sudo journalctl -u unbound -f
sudo tail -f /var/log/pihole/pihole.log
```
